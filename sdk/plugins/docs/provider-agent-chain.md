# Provider 到 Agent 配置、请求观测与恢复

同一 Provider 可以按明确授权使用预设、模型目录、协议转换和有限配置计划。这些能力共用领域契约，但不共享 guest、目录权限、网络授权或凭据。安装或启用一个包不等于完成连接，也不授权其他包。

## 能力与宿主边界

| 能力           | 已有外部声明 / 示例                           | 统一契约与执行边界                                                                              |
| -------------- | --------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| 静态预设       | `provider.catalog@1` / `provider-presets`  | `PresetAdapter` 只给初始值；选择时核对签名，Provider 身份与保存归宿主                           |
| 模型目录       | `provider.models@1` / `model-catalog`      | `ProviderAdapter` 的受控路径及解析；宿主持有精确 Draft / Saved 范围、凭据注入和发布裁决         |
| 原生配置       | 内置 Agent 配置适配                           | `ConfigPlanner` 使用宿主捕获的 JSON / TOML 等原文；预览、确认、备份、写入、回读及恢复由宿主执行 |
| 有限 JSON 计划 | `config.plan-provider@1` / `json-config`   | 同一 `ConfigPlanner` 的有限字段候选；不接收原始文件、路径或真实 Key，宿主复核后代入占位值       |
| 协议转换       | `gateway.protocol@1` / `envelope-protocol` | `ProtocolAdapter` 的 open / feed / finish；宿主负责网络、认证、取消、发送归属、终态和用量       |

旧 manifest、WIT、签名和 IPC 不增加未知字段。多个包通过宿主的 Provider ID 及精确版本关联，不直接互调。一个预设的名称和协议也不能替代实际目录或协议绑定。

## 完整操作顺序

1. 检查签名包并明确启用；预设、目录、协议、配置文件分别授权。
2. 在原添加窗口选择预设，编辑 Endpoint、名称与模型初始值，输入新 Key。选择预设不准备凭据或发起网络请求。
3. 沿原新 Key 流程准备宿主凭据。明确选择目录来源；外部目录使用当前地址、协议、供应商、凭据引用和原数据库身份的 Draft 授权。
4. 读取完整目录并选择模型，保存原 Provider / 来源请求。重读或重放同一 operationId 只读取原结果，不重做网络或写入。
5. 对要发布到 Agent 的模型独立验证。目录存在不等于模型可用；OpenCode 等完整模型分组继续要求各启用模型的有效验证。
6. 如使用外部协议，对已保存 Provider 单独绑定当前签名版本。预设复制、目录读取、有限 JSON 计划均不产生该授权。
7. 在 Agent 配置入口生成预览，核对原文件修订、Provider 修订、选定模型和影响范围，再明确应用。宿主保存加密备份，原子写入后回读。待应用、已写入、待重启和实际运行分别显示。
8. 客户端按生成的本机入口和本机凭据发送请求。上游 Key 留在宿主；OpenCode 配置使用本机入口 Key，Claude Code 使用宿主凭据 helper。配置成功不能作为真实 Agent 或真实模型调用成功的证据。
9. 在调用页核对逻辑请求、实际尝试、Provider / Agent 身份和用量；原始尝试页与聚合请求页的单位不同。缺少 Session 或项目证据时保留未知。
10. 根据当前结果与文件修订，使用原操作核查、取消、配置恢复或明确结束草稿引用。恢复不要求重新启用、重新信任或重装已移除插件。

有限 JSON 配置计划只修改用户明确选择的文件和声明字段。它不自动变成原生 Agent 格式适配器；本机 Agent 切换仍由对应的内置格式适配器负责。原文件中的其他字段、权限和未知配置保持。

## 停用、撤权和卸载

静态预设失效不改写已复制输入或已保存 Provider。目录来源失效保留原选择与原回执，不默默读取内置目录。绑定的协议失效须明确失败；发送后撤权、中断或终态未知不能触发第二次发送，也不能补造成功结束或 usage。

协议保护继续生效：存在协议绑定时，卸载会以 `protocol_binding_active` 拒绝。先保留失败证据和配置恢复能力，明确解除绑定后才能卸载。解除绑定是用户选择，不能由失败处理自动执行。不要把“解除绑定后允许后续新请求使用内置基础协议”与“失效绑定自动回退”混为一谈。

加密备份、原 Provider、操作结果及配置恢复身份不随包卸载删除。文件被其他程序修改时恢复先拒绝；不能覆盖修改、伪造新预览，或在未知结果时重做原请求。配置恢复、有限计划恢复和草稿目录引用收尾分别使用原领域入口。

## 可重复的受管链路验证

`scripts/test-provider-agent-chain.mjs` 使用临时数据、MemoryVault、三个实际 Wasm 示例和一个声明式包，以及回环合成上游。它从预设与 Key 创建原 Provider，经真实目录和独立验证生成 OpenCode 配置；受管 HTTP 客户端实际消费该配置和本机 Key，经过协议 worker 返回 UTF-8 流，再核对原始尝试、聚合调用和详情。

验证继续覆盖在途撤权、不重复发送、原卸载保护、显式解除、四包移除后的宿主独立恢复、外部修改冲突，以及显式内置链路和 Claude Code 配置应用 / 精确恢复。所有包、测试文件和上游均归该运行所有，不使用用户真实会话或 API 账户。

该脚本不启动真实 Agent，不执行会访问系统钥匙串的凭据 helper，不调用真实模型，也不能代替打包窗口的原生选包、键盘、滚动和确认流程。MemoryVault 的进程生命周期不能证明真实 Keychain 的重启持久性。DSH、真实 Keychain 专项、Developer ID 和正式公证仍须分别保留未验证状态。
